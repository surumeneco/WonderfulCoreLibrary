# WCL 0.1.0 / WWC 2.1.0 / WWW 1.1.0 — pre-release acceptance

Status: **integration candidate; NOT a production-release authorization**. This checklist is the remaining field gate after code + all current integration CI are green. Record actual build commit SHA, JAR SHA-256, paper build and result for each run. A successful Gradle/Actions build is not a Paper runtime pass.

## 1. Candidate and artifact traceability

| Component | Expected version | Source | Build artifact |
| --- | --- | --- | --- |
| WonderfulGenomeLib | 1.0.1 | WGL `develop` matching candidate CI | corresponding WGL plugin JAR |
| WonderfulCoreLibrary | 0.1.0 | WCL `develop` | `wcl-plugin/build/libs/WonderfulCoreLibrary-0.1.0.jar` |
| WhatAWonderfulChicken | 2.1.0 | WWC `develop` | `build/libs/WhatAWonderfulChicken-2.1.0.jar` |
| WhatAWonderfulWolf | 1.1.0 | WWW `develop` | `build/libs/WhatAWonderfulWolf-1.1.0.jar` |

- Fetch artifacts from the **successful run for the recorded commit** in each repository's GitHub Actions; do not substitute older runs or infer JAR version from filename alone.
- WCL's single deployable JAR is the `wcl-plugin` result: API/core are included in it. Do **not** copy the independent `wcl-api` or `wcl-core` JARs into `plugins/`.
- WWC and WWW depend on **both** `WonderfulGenomeLib` and `WonderfulCoreLibrary` at runtime. Neither consumer JAR may bundle WGL/WCL classes.
- Examine each built JAR's `plugin.yml` (e.g., `unzip -p file.jar plugin.yml`), check declared name/version/main/depend and verify that placeholders were expanded. Inspect class paths if the static CI check did not already supply this evidence.
- Preserve the old production JARs and a restorable snapshot of worlds, plugin data and external Genome files. Test against a **copied server/data set**, never perform a corruption/migration test on live data.

## 2. Environment / enable and disable

Use a Paper 26.2 staging server with the same relevant plugin and Geyser/Floodgate environment as production. Record Java runtime version and exact Paper build.

- [ ] Cold start with all four version-matched JARs: WGL/WCL enabled before the two consumers, no `ClassNotFoundException`, `NoClassDefFoundError`, service lookup failure, `LinkageError`, or duplicate class.
- [ ] Confirm no WCL-owned `config.yml`, `lang`, default gameplay settings, independent global ticker or world scan. Consumer-specific config/data remain at their existing locations.
- [ ] Stop and restart the staging server; all four re-enable, existing stored individuals remain accessible and no owner context/task survives an outdated plugin instance.
- [ ] On a disposable server test missing WCL/WGL and disabled providers: consumers must fail clearly without destructive fallback; check re-enable/reload lifecycle only if supported by their documented contract.
- [ ] Record full startup/shutdown logs, `plugins` status and the exact tested JAR hashes.

## 3. Behavior and persisted-data regression (both WWC and WWW)

Test against a restored copy of *pre-migration* data and against newly created individuals. Compare before/after results. Record outcomes separately for WWC and WWW.

- [ ] Biological clock: normal passage, sleep skip, command/custom time skip, non-qualifying skip, world change/restart; existing YAML keys and values persist without offset drift.
- [ ] Age and rank: juvenile/adult/elder stages, growth threshold edges, ability rank boundaries, negative/invalid values where relevant; retain consumer-specific validation semantics.
- [ ] Genome: spawn/founder distribution, breeding parent identity, mutation/inheritance/trait selection, marker and pedigree, and original WGL decoding. Validate identical random seed/draw order on deterministic fixtures.
- [ ] WGPF/Genome payload: original bytes/schema and CRC are readable, world-specific paths and persisted external files remain compatible; move/copy between worlds and reload/rollback on a staging clone. Detect same-UUID collisions, including a not-yet-loaded world's records.
- [ ] Commands: existing SNBT-like inputs, escaping, config get/list/set/reset and Tab suggestions, invalid path and missing/extra arguments; unchanged permission and error behavior.
- [ ] Traits: active-source transition `0→1` starts work and `1→0` stops it; WWC clears its alert bookkeeping; WWW maintains an in-flight HolyPulse without recurring traits; verify effects, duration and third-party stronger potion effects.
- [ ] Navigation, ride/GUI and actions: species-specific movement/repath, tame/follow/guard, equipment/inventory GUI, owner/commander behavior, traps and combat remain unchanged.
- [ ] External inventory reads: loaded and saved/offline WWC/WWW, equipment and all storage slots including WWC Shulker contents, nonempty/empty, PDC-bearing items, nested containers, duplicate identities, mutating a returned snapshot, invalid/corrupt/unsupported records; failures must **not** masquerade as an empty inventory.
- [ ] Repeated world unload/reload, chunk unload/reload, stop/restart and owner changes; no stale entity instance, stale async result or duplicated service registration.
- [ ] Repeat relevant input, GUI, inventory, follow/ride/trap observations from both Java Edition and Bedrock Edition via Geyser. Note JE/BE-specific deviations independently.

## 4. Performance and release decision

Use equal world copies, loaded individual counts, players, settings and observation windows for the baseline (released WWC 2.0.1 / WWW 1.0.1 / WGL 1.0.1) and candidate (WWC 2.1.0 / WWW 1.1.0 / WGL 1.0.1 / WCL 0.1.0). Warm up both configurations before capture.

- [ ] Gather CPU usage, TPS, MSPT median/p95/p99, GC/allocation, task/event work count and main-thread stalls; separately exercise idle populations, active trait/combat, spawning/traps and mass chunk load.
- [ ] Confirm no meaningful CPU/MSPT or memory regression, no unbounded queues, and no changes in observable timing/encounter opportunities. Investigate failures before acceptance; an equal scheduler count is not proof.
- [ ] Preserve comparable profiles/timings and the reproducible test scene, with run IDs, build SHA and profiler version.

## 5. Gate / handoff

`develop` and CI green represent **code integration only**. Do not merge the unreleased candidate to `main`, cut a version tag, issue a GitHub Release, or replace the production JARs until the staging JE/BE + persistence + performance gates above are accepted.

Record one of **PASS / FAIL / NOT RUN** for every checklist line, logs and defects. At handoff, the only human-dependent step is staging/real-client acceptance and the production deployment decision. If acceptance passes, record the tested commit SHAs and exact JAR hashes, then promote the same source/JAR set in WCL → WWC/WWW dependency order; verify that `main`, tag, distributed JAR, deployed JAR and boot log agree.
